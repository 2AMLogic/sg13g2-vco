# Post-#79 elaboration / start-up check on the fleet (issue #94, increment: `design/run_elaborate.sh` item)

Append-only. Request, netlist body, inductor model and retained evidence:
`sim/oscillator-core/klt-sim/elaborate-post79/` (`request-elaborate-post79.json`, `vco_core_body.spice`,
`sg13g2_inductor_em.spice`, `evidence/` = `report.json`, per-unit `corner.cir` + `ngspice.log`, `batch-receipt.json`).
Two earlier submissions of a defective measurement card are kept beside it (`evidence-attempt1-td-misplaced/`,
`evidence-attempt2-td-targ-only/`) and explained under Limits; neither is used for any number below.

## What this is and is not
The fleet equivalent of the three questions `design/run_elaborate.sh` asks (elaborates against the pinned PDK with the
real OSDI varactor? starts up and oscillates at Vctrl = 0, 1.65, 3.3 V from a 10 mV differential `.ic`?). It
**cannot be the script itself**: the script runs `sim/tools/build-osdi.sh` and needs a local `mosvar.osdi`, which this
host does not have (the reason PR #288's local attempt failed). It grades **no** spec row.

## Method
- Netlist: `design/vco.spice` (sha256 `090983d6...49404`, main @ `ac2481d`), device section only
  (`vco_core_body.spice`, sha256 `9ce081a6...f6155`, the same body as the #290 re-measure request, which adds only the
  `Bvcm` observer line to the #285 body). `.ic v(OUTP)=3.305 v(OUTN)=3.295` is present. The `netlist.sh --check`
  freshness step of the script (xschem) was **not run**; this record is evidence about the committed `vco.spice`, not
  a derivation check of `vco.sch`.
- Corner: tt (`mos_tt`/`hbt_typ`/`cap_typ`), 27 C, Vctrl in {0, 1.65, 3.3} V; `tran 1p 20n 0 2p`; window 10-20 ns.
- OSDI: `options.osdi_preload` = `$PDK_ROOT/ihp-sg13g2/libs.tech/ngspice/osdi/mosvar.osdi`
  (`/opt/pdk/...` on the runner). The generated `corner.cir` issues `pre_osdi` on it; the ngspice log carries no model-resolution error and no unknown-subckt line (the log does not print the OSDI load itself).
  **OSDI ABI version actually loaded: not reported by the runner and not measured here.** The runner's OSDI/compiler
  digests are likewise unreported.
- Route: `klt sim --backend batch`, 3 units, fleet job `klt-sim-f4ece327a446` (m6i.4xlarge spot, us-east-1d), ngspice-46,
  runner klt 0.9.0 / client 0.9.1.dev102, `runner_compatibility: match`, `runner_request_features: supported`. PDK
  `fetched:0.3.0`; stamp unreadable (`not_comparable`), so equality with `sim/pdk.json` is **not verified**.
  Nothing ran locally.
- Estimator: period from two `.meas ... WHEN v(vdiff)=0 RISE=k TD=10n` crossing times (k=1 and k=11):
  f = 10 / (t11 - t1). Peak values are `MAX/MIN` over 10-20 ns. This is a 10-period count, the same class as the
  script's `osc_metrics`, not the trapezoid-mean/method-checked extractor; it states no phase noise.

## Limits
- One corner, one temperature, one 10-period window, one realisation per point: no variance. 125 C was **not** run here;
  it remains the recorded first-timepoint abort (`20261103-185500-666800d-hot-startup.md`).
- Attempts 1 and 2 used a `TRIG ... TARG ...` card with `TD=10n` misplaced; they returned a negative (-7.6 ns) and an
  implausible (12.3 ns) "10-period" time because ngspice applies `TD` to only one clause. Their other columns match this
  run to the printed digits. The two-`WHEN` form above is the one used.
- `t_cross_*` were not cross-checked against a raw waveform (not retained); the frequency is a 10-crossing count.
- The 0.3066 mA supply current is the 10-20 ns mean from `.meas AVG i(vsup)` (sign flipped: source current).
